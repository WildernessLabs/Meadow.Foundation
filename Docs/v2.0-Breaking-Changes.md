# Meadow.Foundation v2.0 — Planned Breaking Changes

This document captures breaking changes proposed for the next major version. Each item includes the motivation, the impact on existing code, and the migration path.

---

## 1. Eliminate `ChangeResult<UNIT>` boxing in the notification chain

**Motivation**

`ChangeResult<UNIT>` is a `struct`, but the internal notification chain accepts `IChangeResult<UNIT>` (an interface), which boxes the struct on every sample cycle. With multiple sensors running this is a continuous source of GC pressure on a memory-constrained device.

**Root cause**

`ObservableBase<UNIT>` implements `IObservable<IChangeResult<UNIT>>` and `FilterableChangeObserver<UNIT>` implements `IObserver<IChangeResult<UNIT>>`. The `IChangeResult<UNIT>` generic type parameter is the interface, so boxing is unavoidable without changing the type throughout.

**Proposed change**

Change the generic type parameter from `IChangeResult<UNIT>` to `ChangeResult<UNIT>` throughout:

```csharp
// Before
IObservable<IChangeResult<UNIT>>
IObserver<IChangeResult<UNIT>>
FilterableChangeObserver<UNIT> : IObserver<IChangeResult<UNIT>>

// After
IObservable<ChangeResult<UNIT>>
IObserver<ChangeResult<UNIT>>
FilterableChangeObserver<UNIT> : IObserver<ChangeResult<UNIT>>
```

**Impact**

- `RaiseEventsAndNotify(IChangeResult<UNIT>)` signature changes in all ~170 drivers that override it
- All user `Subscribe()` / `CreateObserver()` call sites change handler lambda signatures
- The `Updated` event signature changes

**Side effect (improvement)**

Currently `FilterableChangeObserver.OnNext` mutates `result.Old` through the shared interface reference — all observers in the list see each other's `lastNotifiedValue` mutations. Passing by value gives each observer an independent copy, fixing this subtle correctness bug.

## 2. `ReadSensor()` return type: `Task<UNIT>` → `ValueTask<UNIT>`

**Motivation**

60+ peripheral drivers implement `ReadSensor()` by returning `Task.FromResult(value)` — a synchronous result wrapped in a heap-allocated `Task<UNIT>` object. This allocates one `Task` per sample cycle per sensor. `ValueTask<T>` avoids the allocation entirely when the result is already available synchronously, which is the common case for I2C/SPI reads.

**Proposed change**

```csharp
// Before
protected abstract Task<UNIT> ReadSensor();
public virtual Task<UNIT> Read();

// After
protected abstract ValueTask<UNIT> ReadSensor();
public virtual ValueTask<UNIT> Read();
```

**Impact**

- All ~60 drivers that return `Task.FromResult(value)` change to `return value;` (or `new ValueTask<UNIT>(value)`)
- Any driver that genuinely awaits async I/O inside `ReadSensor()` can still `return new ValueTask<UNIT>(someTask)`
- Callers of `Read()` change from `await Read()` to `await Read()` — no change at the call site
- `Read().GetAwaiter().GetResult()` in `PollingSensorBase` works unchanged

**Migration**

```csharp
// Before
protected override Task<Temperature> ReadSensor()
{
    var temp = ReadTemperatureFromDevice();
    return Task.FromResult(temp);
}

// After
protected override ValueTask<Temperature> ReadSensor()
{
    var temp = ReadTemperatureFromDevice();
    return temp;  // implicit ValueTask<Temperature>
}
```

## 3. Remove redundant `Updated` event from `SamplingSensorBase`

**Motivation**

Every sensor exposes both `event EventHandler<IChangeResult<UNIT>> Updated` and `IObservable<IChangeResult<UNIT>>`. They carry identical data. The event requires an extra `Updated?.Invoke()` call on every sample (with its own boxing), and the dual mechanism adds cognitive overhead for driver authors and consumers.

**Proposed change**

Remove `Updated` from `SamplingSensorBase` and `RaiseEventsAndNotify`. The observable pattern via `Subscribe()` / `CreateObserver()` is the single notification mechanism.

**Migration**

```csharp
// Before
sensor.Updated += (s, e) => Console.WriteLine(e.New);

// After
sensor.Subscribe(Sensor.CreateObserver(result => Console.WriteLine(result.New)));
```

**Impact**

- All existing event-based subscriber code must migrate to the observable pattern
- Driver overrides of `RaiseEventsAndNotify` are simplified — no event invocation needed

---

## Notes

- Items 1 and 3 should land together since they both affect the notification chain signature
- Item 2 is independent and can land separately
- All three items were identified during a performance audit of the sensor base classes (March 2026)
